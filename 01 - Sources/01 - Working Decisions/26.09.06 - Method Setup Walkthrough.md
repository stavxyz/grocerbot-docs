# Method Setup Walkthrough, 2026-09-06

Recorded from the chat session in which the GrocerBot documentation repo was first set up. Claude had reviewed the docs repo, then read `grocerbot-orchestrator` and `grocerbot-core` in depth, then asked Sam one question at a time. Decisions are recorded in the words that carried them, with the firmness Sam gave them.

## Context Sam gave before the questions

- The method and repo came from Buck, who built them for his product DRAPER. Some of it is DRAPER-specific. The example folder and the example pages in Figma are worth keeping to see how DRAPER did it. GrocerBot is a wildly different product.
- The aim is to apply the same system to the substance of GrocerBot's functionality, code, data, database structure, and data table structures, and visualise that.
- The root Function and Logic files are Buck's way of splitting a system prompt into a function plus logic blocks. `Logic - Harness.md` is simply a logic block explaining DRAPER's central harness so it need not be re-explained every run.
- There is no AI inside GrocerBot at this time. The whole system of systems is deterministic, as it stands and as it is designed today. So DRAPER's Function and Logic levels and its trigger, prompt, inputs, outputs, logic record do not apply.
- The lion's share of context, artifacts, and sources are in GitHub, checked out at `~/src/grocerbot-orchestrator` and `~/src/grocerbot-core`.
- The Figma MCP is already wired up in Sam's Claude Code.

## Decisions

**1. Boundary.** The system is grocerbot-orchestrator plus grocerbot-core. The graftpunk BEK plugin and the Cloudflare email worker are in-scope Piping. The legacy `grocerbot` CLI is version 1; it is documented only as a contrast to version 2, "the new hotness with tenancy being built to become a SaaS product". Sam: "that boundary matches. i haven't thought much about how or if we want to document legacy other than contrasting differences between version 1 (legacy) and version 2".

**2. Standings.** The harness describes the full version 2 shape as the aim and stamps each part live in prod, live in dev only, or designed and not yet wired. Sam accepted three standings but does not want the Figma project to become a project management or status tracker: "visual view of the workflows/diagrams/design is more important than showing what is live or not yet wired or in dev". Standings live in the harness text. Boards show the design. Sam does not want to come back to Figma every time a PR ships, "unless, of course, that updating can happen automatically". Automation is out of scope for now.

**3. Parts.** Seven parts, agreed "for now": vendor portal monitoring; email ingestion; notification delivery; document canonicalization; POS sync; inventory ledger; reliability and operations. Tenancy and configuration are cross-cutting properties, not a part.

**4. Sources.** Pointers with recorded SHAs, not copied snapshots. `dev` is the branch of record. Sam: "pointers with SHAs, dev is the branch".

**5. Levels.** Four: Principles, Process, Data, Piping. Sam had listed Process, Data, and Piping; Claude recommended keeping a Principles level holding the seven stated engineering rules found in the code and specs, one sheet each. Sam: "i like your recommendation".

**6. Figma file.** Sam pointed at `https://www.figma.com/design/nBmhDyEDpFPrMq0ztmHDb0/`, "or create a new one, whatever you want to do". The existing copy was used. Its first read exhausted the Starter plan's twenty MCP calls a month; Sam upgraded to Professional the same day: "i had to upgrade figma to professional so we could get more mcp calls."

**7. Operation.** The word for the tag on the links inside Process. Claude recommended Operation over Connection and Action because the same tag also stands alone inside card panels. Sam asked "why not Connection if it is in fact representing something that links one thing to another? I'm open to operation as well", heard the reason, and ruled: "operation it is, go ahead."

**8. Standing instruction.** Sam: "for the duration of this chat instead of vaguely describing 'things that need my eyes' and then producing stream of consciousness prose please always just ask me one question at a time."

**9. Rail density.** The Part 1 rail carries the tight cut: roughly ten operations that change what the store knows; bookkeeping steps (unique lock, enqueue audit row, workflow runs, dedup registration) appear as Operation fields inside the Piping and Data cards that perform them. Sam: "tight cut, go ahead." This also settles the Process versus Piping boundary for bookkeeping: it is Piping, shown on the card.
