# grocerbot-core

The executing service. A FastAPI request and response service that owns the canonical document pipeline, tenancy, the POS subsystem, and the inventory ledger. It touches no job queue. The orchestrator calls it through a generated client.

## What it can support

- Every endpoint, its reads, writes, state transitions, and error shapes at the SHA read.
- Every table, column, key, and index in the core database, and which code writes and reads each.
- The canonical format in full: the three facets, the line item, the pack size, the sellable SKU.
- The POS plan, apply, reap, and witness behaviour, and the Clover adapter's field mapping and limits as encoded.
- The ledger model and what feeds it.
- The seeded vendors and their mappings as of the SHA.

## What it cannot support

- Whether `dev` is deployed to any environment. Unverified.
- Whether the seeded column mappings are correct. `CLAUDE.md` itself says they were guessed from fixture headers, not derived from the legacy supplier modules.
- Clover's actual platform behaviour beyond what the adapter and the POS spec encode from a 2026-07-18 probe.
- Anything about the orchestrator.

## Known stale material inside the repo

`CLAUDE.md` describes the service before tenancy, document types, PDF parsing, the POS subsystem, and the inventory ledger. Twenty-two contradictions with the code were found on 2026-09-06. The load-bearing ones:

- It names `InvoiceRecord` and the `invoices` table; the class is `DocumentRecord` on `documents`.
- It names `ParsedInvoice`, `AssimilatedInvoice`, `CanonicalInvoice`; the dataclasses are `ParsedDocument`, `AssimilatedDocument`, `CanonicalDocument`, and the canonical shape is three facets, not `metadata` plus `line_items`.
- It documents `POST /v1/invoices/upload` and `GET /v1/invoices`; upload lives under `/v1/tenants/{tenant_id}/` and the bare list was removed.
- It says upload writes `state=created` and parse writes `state=parsed`; upload parses inline and writes `underivative`, and neither `created` nor `parsed` is ever written by a handler.
- It says three vendors are seeded; four are (`alberts`, `bek`, `glazers`, `unfi`). Only `bek` has metadata mappings.
- It says "zero POS-specific code" and puts POS adapters in a future repo; a Clover adapter with live HTTP calls ships here.
- It lists five required env vars; `POS_CREDENTIALS_KEY` is also required and the app refuses to boot without it.
- It says about 148 tests; there are about 571.
- Its endpoint list omits tenants, tenant vendor settings, order confirmation upload, metadata mappings, `/health/ready`, and all of `/v1/pos/*`.

`docs/POS_BACKENDS.md` and `docs/CANONICAL_FORMAT_ANALYSIS.md` were carried from version 1 and describe its backend model.

## Findings in the code itself

Surfaced for the owner and not yet discussed.

- `audit_log` has an ORM model and no reader or writer anywhere.
- The `pos_plans.report` column is reserved and never written or read; the report is computed live.
- `POST /v1/tenants` and `GET /v1/tenants` are ungated, and all four `/v1/vendors` routes are global with no tenant scoping. The principal is always `TrustedCaller` at version `0.3.x`.
- The inventory ledger is reachable only through the POS planner and pull. No endpoint or CLI command reads or writes it directly.
- Only `invoice` documents feed POS plans. Order confirmations are canonicalized and never planned.
- `gbc pos plan-reject` is a bare status flip and leaves orphaned created items behind, marked `TODO(#42)` in the code.
- `alberts` is seeded with no `quantity_ordered` mapping, so assimilate returns a 422 for it unless the mapping is supplied at runtime.
