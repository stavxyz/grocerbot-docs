Draper. How it ran. How it will run.

Both sides do the same job. You do something in the app, a request goes to a model, a result comes back and lands somewhere. The difference is what decides what goes into that request and where the result goes. On the left, code decides, and it decides differently for every feature. On the right, a record you edit decides, and one piece of code runs it.

Before. Built one feature at a time.

Five kinds of prompt thing. Three ways of assembling a call. A separate piece of code for every place a result can land. Which one you got depended on which feature you were using.

Why it hurt

To change what a call did, you had to find which of the five kinds it was, which path ran it, and where its text and inputs lived. Then change code.

Rules that should be shared, like the research standard, the voice, the evidence rules, were pasted into many prompts. A fix in one did not reach the others.

Nothing recorded exactly what entered a call or where the result went. Bad output had no single place to look.

Behavior lived in code. Five flavors, assembled three ways, landing five ways.

After. One record, one harness.

Every model call is a Function: a record you and Erik edit in the admin. A trigger finds it in the registry. The harness, which is code, assembles it from the libraries, sends it, and routes the result to the output the record selected.

8Outside the harness. Plain code, one job each.

No model, no judgment, nothing to attach. A click or an event, then one write. These stay as small custom code. They are not Functions.

Code
Approve, Deny, Edit

On the doc card. Approve flips the row to approved and bumps its version. Deny drops the draft. Edit opens it. One field change. Approve is also what the next Function's trigger can listen for.

Code
Tray add

You confirm items a search showed you. They are added to that tray module. A list of ids into a table.

Code
Save, upload

An image, a doc, a plug-in capture becomes a row plus a stored file. That row landing can trigger a Function, for example Reference Read. The save itself is just storage.

Code
Syncs from outside

Read.ai transcript to a Notion record. PandaDoc signature and Mercury wire to status fields. Notion status to app stage. Field for field copies between tools.

Code
Export, download

Tray download, Atlas folder export, file handoff. Package what exists and hand it over.

Run log

Every run records which Function ran, exactly what it read, which logic it carried, and what it wrote. Bad output: open the run and see everything.

Behavior lives in records you edit. One harness assembles, runs, and routes them.

Read across. Each row on the left has the same row on the right. What you do, what fires, what goes into the call, the model, where it lands. On the left each is answered per feature, in code. On the right each is a field on one form, read by one harness.
